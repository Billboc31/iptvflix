# T038 — Build a bounded local discovery candidate pool from external metadata

## Objective

Add a persisted `discovery_candidates` table and a `DiscoveryCandidatePoolService` that fetches bounded slices of TMDB discovery feeds (popular, trending, upcoming), upserts them with TTL-based expiry, deduplicates against canonical `movies`/`series` rows, and allows promotion of any candidate to a canonical Media record.

## Included

### 1. Extend `MetadataProvider` interface — `apps/api/src/providers/metadata/types.ts`

Add a `DiscoveryFeed` union type and two new methods to `MetadataProvider`:

```ts
export type DiscoveryFeed = 'popular' | 'trending' | 'upcoming'

// Added to MetadataProvider interface:
fetchMovieFeed(feed: DiscoveryFeed, page: number): Promise<MetadataCandidate[]>
fetchSeriesFeed(feed: DiscoveryFeed, page: number): Promise<MetadataCandidate[]>
```

`NoopMetadataProvider` gets stub implementations returning `[]`.

### 2. Implement feed methods in TmdbClient — `apps/api/src/providers/metadata/tmdb/client.ts`

Map each `DiscoveryFeed` to the corresponding TMDB v3 endpoints with `page` forwarded:

| Feed | Movie endpoint | Series endpoint |
|---|---|---|
| `popular` | `/movie/popular` | `/tv/popular` |
| `trending` | `/trending/movie/week` | `/trending/tv/week` |
| `upcoming` | `/movie/upcoming` | `/tv/on_the_air` |

Each call re-uses the existing rate-limit / retry / timeout logic already in `TmdbClient`. Return value is mapped to `MetadataCandidate[]` (same shape as `searchMovies`).

### 3. New schema table — `apps/api/src/db/schema/discovery-candidates.ts`

Table name: `discovery_candidates`

| Column | Type | Constraints |
|---|---|---|
| `id` | `uuid` | PK, default `gen_random_uuid()` |
| `externalId` | `text` | not null |
| `mediaType` | `mediaTypeEnum` ('MOVIE'\|'SERIES') | not null |
| `title` | `text` | not null |
| `year` | `integer` | nullable |
| `synopsis` | `text` | nullable |
| `posterPath` | `text` | nullable |
| `popularity` | `doublePrecision` | nullable |
| `voteAverage` | `doublePrecision` | nullable |
| `releaseStatus` | `text` | nullable |
| `provenance` | `text` | not null — feed name ('popular', 'trending', 'upcoming') |
| `canonicalMovieId` | `uuid` | FK → `movies.id`, nullable |
| `canonicalSeriesId` | `uuid` | FK → `series.id`, nullable |
| `refreshedAt` | `timestamp with time zone` | not null |
| `expiresAt` | `timestamp with time zone` | not null |
| `createdAt` | `timestamp with time zone` | not null, defaultNow |

Constraints:
- Unique on `(externalId, mediaType)` — prevents duplicate provider identities.
- Index on `expiresAt` — efficient eviction queries.
- Index on `(mediaType, expiresAt)` — filtered pool reads.

Re-export from `apps/api/src/db/schema/index.ts`.

### 5. New service — `apps/api/src/services/discovery-candidate-pool-service.ts`

Class `DiscoveryCandidatePoolService` constructed with `(db: Db, provider: MetadataProvider)`.

**Constants** (module-level, not env-driven):
- `CANDIDATE_TTL_DAYS = 7`
- `MAX_PAGES_PER_FEED = 3`
- `FEED_PAGE_DELAY_MS = 250` — inter-page throttle, same pattern as `MetadataEnrichmentService`

**`async refreshPool(feeds: DiscoveryFeed[], mediaTypes: ('MOVIE' | 'SERIES')[]): Promise<void>`**

For each `feed × mediaType` combination:
1. Fetch pages 1…`MAX_PAGES_PER_FEED` sequentially with `FEED_PAGE_DELAY_MS` between pages. Stop early if the provider returns an empty page (natural end of feed).
2. On `TmdbRateLimitError`: stop this feed/type combination, continue others.
3. On `TmdbNetworkError` or other: stop this combination, log, continue.
4. For each batch of `MetadataCandidate[]` received, upsert into `discovery_candidates`:
   - On conflict `(externalId, mediaType)`: update `title`, `year`, `synopsis`, `posterPath`, `popularity`, `voteAverage`, `releaseStatus`, `provenance`, `refreshedAt`, `expiresAt`.
   - Set `expiresAt = now() + CANDIDATE_TTL_DAYS days`.
5. After all upserts, run a single cross-reference pass to populate `canonicalMovieId` / `canonicalSeriesId`:
   - Join `discovery_candidates` (where `canonicalMovieId IS NULL` and `mediaType = 'MOVIE'`) against `movies.tmdbId` on `externalId = tmdbId::text`. Update matched rows.
   - Same for series.

**`async evictStale(): Promise<number>`**

Delete all rows where `expiresAt < now()`. Return deleted count.

**`async materializeCandidate(candidateId: string): Promise<{ movie: Movie } | { series: Series }>`**

1. Fetch candidate row; throw if not found.
2. If `canonicalMovieId` / `canonicalSeriesId` is already set: return the existing canonical row (no-op).
3. Otherwise call `ExternalDiscoveryService.materializeMovie(externalId)` or `materializeSeries(externalId)` (existing method, already deduplicates by `tmdbId`).
4. Update the candidate row to set `canonicalMovieId` / `canonicalSeriesId` to the returned record's `id`.
5. Return the canonical record.

Constructor receives `ExternalDiscoveryService` in addition to `db` and `provider`.

### 6. Tests — `apps/api/src/services/__tests__/discovery-candidate-pool-service.test.ts`

Test cases (Vitest, mocked db + mocked provider following existing service test conventions):

| # | Scenario |
|---|---|
| 1 | `refreshPool` — happy path: N candidates upserted, rows created with correct `expiresAt` |
| 2 | `refreshPool` — idempotency: second refresh on same candidates produces no additional rows (upsert on conflict) |
| 3 | `refreshPool` — cross-links existing canonical Movie/Series when `tmdbId` matches |
| 4 | `refreshPool` — stops after empty page (no extra provider calls) |
| 5 | `refreshPool` — rate-limit on page 2: stores page-1 results, skips remaining pages for that feed/type |
| 6 | `refreshPool` — network error: stores partial results for other combinations |
| 7 | `evictStale` — deletes expired rows, leaves fresh ones, returns correct count |
| 8 | `materializeCandidate` — already linked: returns existing canonical without calling `ExternalDiscoveryService` |
| 9 | `materializeCandidate` — not yet linked: calls `ExternalDiscoveryService`, updates candidate row, returns new canonical |
| 10 | `materializeCandidate` — unknown candidateId: throws |

## Excluded

- Recommendation scoring or ranking against the candidate pool.
- Taste-profile generation or consumption.
- Any HTTP route exposing the candidate pool to clients (internal service only).
- TMDB genre-discovery endpoint (`/discover/movie?with_genres=…`) — feed-based popular/trending/upcoming is sufficient for this ticket; genre filtering is a follow-up.
- Importing or syncing the entirety of TMDB's catalog.
- Scheduler / cron wiring for automatic pool refresh — callers trigger `refreshPool` explicitly.
- LLM-based features.

## Acceptance criteria

- `discovery_candidates` table is created by migration `0018` and the migration chain is unbroken (`drizzle-kit check` passes).
- `MetadataProvider` interface declares `fetchMovieFeed` and `fetchSeriesFeed`; `TmdbClient` implements them; `NoopMetadataProvider` stubs return `[]`.
- `refreshPool(['popular', 'trending', 'upcoming'], ['MOVIE', 'SERIES'])` called twice in sequence on a clean DB produces exactly the same number of rows both times (idempotent upsert verified by test 2).
- Candidate rows carry `externalId`, `mediaType`, `provenance`, `refreshedAt`, `expiresAt`; no Availability column exists on the table.
- When a candidate's `externalId` matches `movies.tmdbId`, `canonicalMovieId` is populated after `refreshPool` (test 3 passes).
- `evictStale` removes only rows with `expiresAt` in the past (test 7 passes).
- `materializeCandidate` does not create a duplicate `movies`/`series` row when the canonical already exists (test 8 + reliance on existing `ExternalDiscoveryService` deduplication logic).
- All 10 test cases pass under `vitest run`.
- No existing tests are broken.
